# Соглашения проекта

## Архитектура Android

Проект следует актуальным официальным рекомендациям Google для архитектуры Android:

- [Recommendations for Android architecture](https://developer.android.com/topic/architecture/recommendations)
- [Data layer](https://developer.android.com/topic/architecture/data-layer)
- [UI layer](https://developer.android.com/topic/architecture/ui-layer)
- [Domain layer](https://developer.android.com/topic/architecture/domain-layer)

Все рекомендации Google с приоритетом **Strongly recommended** считаются обязательными. Отступление
допускается только при наличии технической причины, зафиксированной в документации проекта.

### Границы слоёв

- `ui` отображает неизменяемый UI state и передаёт действия пользователя вверх по принципу UDF.
- Экранное состояние с доступом к данным принадлежит `ViewModel` и публикуется через `StateFlow`.
- Compose собирает `Flow` только с учётом lifecycle, например через `collectAsStateWithLifecycle`.
- `data` содержит репозитории, источники данных, модели приложения и основную бизнес-логику.
- UI и `ViewModel` не обращаются к data source напрямую — только к репозиторию или use case.
- Каждый репозиторий определяет единственный источник истины и предоставляет изменения через
  `Flow`; одноразовые операции оформляются как main-safe `suspend`-функции.
- `domain` является опциональным. Он создаётся только для сложной или переиспользуемой между
  несколькими `ViewModel` логики и содержит stateless use case с именами вида `VerbNounUseCase`.
- Направление зависимостей: `ui → domain → data`; если domain не нужен, допускается `ui → data`.
- `core` содержит только переиспользуемые технические абстракции и не зависит от UI или data.
- Android-типы не проникают в `data`, `domain` и платформенно-независимую часть `core`.

### Состояние, асинхронность и зависимости

- Публичные модели состояния неизменяемы; изменять данные может только владеющий ими слой.
- Межслойное взаимодействие выполняется через coroutines и `Flow` с корректной передачей отмены.
- Data- и domain-API обязаны быть main-safe; диспетчеры передаются явно и заменяются в тестах.
- Зависимости создаются через Hilt, их scope соответствует владельцу состояния и документируется.
- Время, случайность, ввод-вывод и внешние SDK скрываются за тестируемыми границами.
- Для бизнес-логики обязательны unit-тесты, включая ошибки, отмену и граничные состояния.

## Именование интерфейсов

- Интерфейсы называются по роли без технического префикса, например `PointSourceRepository`.
- Реализация уточняет способ выполнения контракта, например `InMemoryPointSourceRepository`.
- Имя файла совпадает с именем находящегося в нём интерфейса.
- Имена интерфейсов Android, Kotlin и сторонних библиотек не изменяются.

## KDoc

- Публичные архитектурные контракты, модели и реализации документируются через KDoc.
- Документация описывает ответственность, жизненный цикл, многопоточность, ошибки и другие
  неочевидные гарантии, а не повторяет имя декларации.
- Публичные члены интерфейса описывают поведение, обязательное для каждой реализации.
